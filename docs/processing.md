# 変換処理の設計と根拠

各判断の根拠を実データの数値とともに残します。
元データ側の性質は [data.md](data.md) を参照してください。

例はすべて実際の出力から採っており、`output/` の該当行と突き合わせて確認できます。

## 通しの例

慈啓会病院（ID `0111010000090`）を例に、入力から出力までを追います。
この施設は運営主体の除去、定期週、休診日、そして OSM に対応値の無い診療科の
振り替えを、すべて通ります。

施設票にはこう入っています。

```
正式名称     社会福祉法人　札幌慈啓会　慈啓会病院
フリガナ     シャカイフクシホウジン　サッポロジケイカイ　ジケイカイビョウイン
英語表記     Jikeikai Hospital
毎週フラグ   月=1 火=1 水=1 木=1 金=1 土=1 日=0
祝日に休診   0
定期週       第1,3,5週の土が休み（日は全週休み）
その他休診日  01月01日，01月02日，01月03日，12月30日，12月31日
```

診療科と診療時間の票には7診療科が並びます。

```
01001 内科           帯1 月=09:00-12:30  帯2 月=13:30-17:30  帯3 土=09:00-12:30
01020 消化器内科      帯1 月=09:00-12:30  帯2 月=13:30-17:00  帯3 土=09:00-12:30
01027 漢方内科        帯1 月=09:00-12:30  帯2 月=13:30-17:30
01028 老年内科        帯1 月=09:00-12:30  帯2 月=13:30-17:30  帯3 土=09:00-12:30
07001 精神科          帯1 月=09:00-12:30  帯2 月=13:30-17:30
09003 リハビリテーション科  帯1 月=09:00-12:30  帯2 月=13:30-17:00
09005 放射線診断科      帯1 月=09:00-12:30  帯2 月=13:30-17:30  帯3 土=09:00-12:30
```

これが次のタグになります。

```
name                  慈啓会病院
official_name         社会福祉法人　札幌慈啓会　慈啓会病院
short_name            慈啓会病院
name:en               Jikeikai Hospital
opening_hours         Mo,Tu,We,Th,Fr 09:00-12:30,13:30-17:30; Sa 09:00-12:30;
                      Sa[1,3,5] off; PH off; Dec 30-Jan 03 off
healthcare:speciality internal;gastroenterology;traditional_chinese_medicine;
                      geriatrics;psychiatry;physiatry;diagnostic_radiology
```

各段階で何が起きたかを追うと次のようになります。

月曜の終了時刻は診療科によって `17:00` と `17:30` に分かれますが、和集合を採るので
遅いほうの `17:30` が残ります。
土曜は帯3にだけ時刻があり、`Sa 09:00-12:30` として独立した規則になります。
定期週の第1,3,5週の土曜休みが `Sa[1,3,5] off` として土曜の規則を上書きします。
日曜は全週休みで、これは毎週フラグの `日=0` と同義なので規則を出しません。
`祝日に休診` が `0` なので `PH off` が付きます。
その他休診日の5日分は、年をまたぐ連続として `Dec 30-Jan 03` にまとまります。
漢方内科は OSM に対応値が無いため `traditional_chinese_medicine` に丸め、その事実を備考に残します。
名称は `社会福祉法人` と `札幌慈啓会` を運営主体として取り除きます。
フリガナは `シャカイフクシホウジン…` と運営主体を含むため `name` と対応せず、`name:ja-Hira` は出力しません。

## 通底する方針

元データの列は書き換えず、変換後の値は別列として持ちます。
判断を覆したくなったときに戻せることと、第三者が対比して検証できることを優先します。
上の例では `official_name` に元の正式名称がそのまま残っています。

判断を含む対応付けはスクリプトに埋め込まず、`mapping/` の CSV に外出しします。
医学的な判断や語彙の当てはめは、レビューして直せる形である必要があります。

除外や保留をした行は、理由とともに全件を一覧に残します。
除外して終わりにしません。

誤った値を出すより出力しません。
OSM では値を書かないコストは低い一方、誤った休診情報を書くと利用者が来院できなくなります。

判定基準は他行との比較ではなく絶対的な基準で行います。
理由が一意に定まり、除外リストから第三者が検証できるためです。
imports メーリングリストで説明とレビューを受ける以上、説明可能性を精度差より優先します。

最後の方針には経緯があります。
当初は中央値と最頻値による外れ値検出を実装しましたが、基準にした中央値そのものが
偏っている施設で正常値を誤検出しました。

```
伊勢崎佐波医師会病院 帯3 小児科  19:30-22:30  →  外れ値と誤判定
  同じコマの中央値は 00:00-08:30（当直枠）
```

夜間コマは母数が少なく、当直枠が中央値になるため、正当な夜間診療が弾かれていました。
絶対基準に切り替えた結果、除外は実データの0.45%まで減り、
最終出力が変わる施設は0.6%にとどまりました。

## opening_hours

### 組み立て

診療科と診療時間の票は1施設につき複数行を持ちますが、OSM の `opening_hours` は
ノードに1つしか持てません。
そこで曜日ごとに全診療科の区間を和集合して畳みます。

```
入力（月曜、7診療科ぶん）
  09:00-12:30, 13:30-17:30, 09:00-12:30, 13:30-17:00, 09:00-12:30, ...
和集合
  09:00-12:30, 13:30-17:30
月曜ぶんの規則（他の曜日と合成する前の中間結果）
  Mo 09:00-12:30,13:30-17:30
```

終了時刻が診療科によって `17:00` と `17:30` に分かれていますが、
和集合なので遅いほうが残ります。

そのうえで施設票の例外ルールを後ろに重ねます。
`opening_hours` は後ろのルールが前を上書きするため、順序が意味を持ちます。

```
基本時間 → 定期週の休み → 祝日 → 特定日の休み → 日付にできない期間のコメント

Mo,Tu,We,Th,Fr 09:00-12:30,13:30-17:30; Sa 09:00-12:30;
  Sa[1,3,5] off; PH off; Dec 30-Jan 03 off
```

`Sa 09:00-12:30` を先に置き、`Sa[1,3,5] off` を後に置くことで、
「土曜は午前診療、ただし第1,3,5土曜は休み」を表します。
順序を逆にすると土曜の休みが時間規則に上書きされて消えます。

### 除外の基準

和集合は最も早い開始と最も遅い終了を採るため、1行の誤入力が施設全体の値を汚染します。
これを防ぐため、外来として明らかに成立しない区間を除外してから畳みます。

| 分類 | 基準 | 件数 | 実例 |
|---|---|---:|---|
| `null_placeholder` | 開始と終了が同一 | 4,473 | `00:00-00:00` |
| `too_early` | 開始が06:00より前 | 2,413 | `00:45-17:15` |
| `too_late` | 終了が23:00より後 | 583 | `09:00-23:59` |
| `overnight_implausible` | 日跨ぎとしても18時間超 | 461 | `15:30-15:00` |
| `sentinel_24h` | `00:00-23:59` の定型 | 201 | 同左 |

全業態で8,131区間、対象の0.5%程度です。
実データを落とした分はさらに少なく、`null_placeholder` を除けば3,658件です。

汚染が是正された例を示します。

```
市立札幌病院
  除外前  Mo,We,Th,Fr 08:45-17:15; Tu 00:45-17:15
  除外後  Mo,Tu,We,Th,Fr 08:45-17:15; PH off
```

火曜だけ別扱いになっていた原因は、耳鼻いんこう科1件の `00:45-17:15` です。
他の26診療科はすべて `08:45-17:15` でした。
`08:45` の打ち間違いとみて `too_early` で除外し、火曜が他の曜日と同じ規則にまとまりました。

### 日跨ぎの扱い

終了が開始より前の区間は日跨ぎ（当直帯）として採用します。
ただし継続時間が18時間を超えるものは、夜勤ではなく打ち間違いとみなします。

根拠は継続時間の分布です。
15時間から16時間に188件が集中する一方、20時間超の11件はいずれも終了が開始の直前にありました。

```
採用する例（全業態で1,663区間）
  19:00-07:00   152件。夜から翌朝までの当直帯（12時間）
  18:00-09:00   104件（15時間）
  17:00-08:30    92件（15時間30分）

除外する例（全業態で461区間）
  19:00-13:00    39件（18時間）
  09:00-07:00    36件（22時間）
  15:30-15:00    霞ヶ浦医療センター 整形外科（23時間30分）
```

採用する側は夕方から夜に始まり翌朝に終わる形で、当直帯として筋が通ります。
除外する側は、朝に始まって翌朝まで続く形（`09:00-07:00`）や、
終了が開始の直前にある形（`15:30-15:00`）で、外来の時間として説明がつきません。
この基準で病院では262件中250件を救済し、12件を除外に残しました。

日跨ぎを採用した施設では、`opening_hours` に翌日へ渡る区間がそのまま出ます。

```
吉岡病院  Mo,Tu,We,Fr 09:00-12:30,15:00-17:30,18:00-08:30; Th 09:00-12:30,15:00-08:30
```

### 24時間営業の表記

日跨ぎのマージ結果が24時間以上になると、開始と終了が同じ表記になります。

```
08:30 開始、翌 08:30 終了  →  08:30-08:30
```

この表記はゼロ長とも24時間とも読めるため、`00:00-24:00` に正規化します。

```
同善病院  Mo,Tu,We,Th,Fr,Sa,Su,PH 00:00-24:00; Dec 30-Jan 03 off
```

### 曜日フラグと時刻の矛盾

全業態で22,195件あります。
性質の異なる2種類が混在しており、一律にどちらを優先することはできません。

A は「フラグは休みなのに時刻がある」ケースで6,168件です。
時刻の中身で判断します。
その時刻が、フラグが営業日と明示している曜日の時刻と同一なら、
記入者が全曜日に同じ値を入れた一律入力とみなしてフラグを採ります。

| 性質 | 判断 | 件数 |
|---|---|---:|
| 営業日と同一時刻 | フラグを採用し、その曜日の時刻をマージ対象から取り除く | 3,874 |
| 独自の時刻 | 時刻を採用し、そのまま残す | 2,294 |

土曜に平日と同じ時刻が入っているのは一律入力と見るのが自然です。
実際の土曜診療なら午前のみが普通で、それは独自時刻の側に現れます。

比較対象を営業日に限るのは、平日自身が休診指定されている場合に、
自分と比較して常に一致してしまうのを避けるためです。

#### フラグを採用したとき、出力はどう変わるか

その曜日の時刻をマージ対象から取り除きます。
結果として、その曜日には時間規則が出なくなります。

```
市立旭川病院  土曜 08:30-17:00（平日の最頻値と同一）

  取り除く前  Mo,We,Fr 08:00-19:00; Tu,Th 08:00-17:00; Sa 08:30-17:00; PH off; Dec 30-Jan 04 off
  取り除いた後 Mo,We,Fr 08:00-19:00; Tu,Th 08:00-17:00; PH off; Dec 30-Jan 04 off
```

`Sa off` のような休みを明示する規則は書きません。
`opening_hours` では、どの規則にも登場しない曜日は閉として解釈されるためです。
土曜を含む規則が1つも無いこの値は、土曜は終日閉という意味になります。

その曜日に定期週の指定があっても、同じく規則が出なくなります。
時刻の無い曜日に `Sa[1,3] off` を書いても意味を持たないためです。

祝日だけは扱いが違い、`PH off` という明示的な規則が出ます。
祝日は月曜から日曜のいずれかに重なるので、規則を書かないと平日の時間規則が
そのまま適用されてしまいます。
病院で「フラグを採用」と判断した255件の内訳は、平日と土日の187件が規則なし、
祝日の68件が `PH off` でした。

時刻を採用した場合は、その曜日の規則がそのまま残ります。

```
札幌鈴木病院  土曜 09:30-12:30（平日は09:00-17:00）

  Mo,Tu,We,Th,Fr 09:00-17:00; Sa 09:30-12:30; PH off; Dec 30-Jan 03 off
```

取り除いた時刻そのものは失われません。
どちらの判断を下した行も、元の値とともに `<業態>_conflicts.csv` に残ります。

B は「フラグは営業日なのに時刻がない」ケースで16,027件です。
これは矛盾ではなく時刻の記入漏れで、休みを意味しません。

`opening_hours` には「開いているが時刻不明」を表す構文が無いため、
その曜日を書かなければ休みと誤解されます。
誤情報を出さないよう、施設単位で出力を見送ります。

```
桑園中央病院
  フラグ  月から金が営業日
  時刻    月火水木のみ。金曜が空
  出力    opening_hours を出力しない
  備考    曜日フラグが営業日とする金曜の時刻が無く、書くと休診と誤解されるため
```

金曜の時刻が無いまま `Mo,Tu,We,Th 09:00-17:00` と書くこともできます。
しかし A と同じ理屈で、規則に登場しない金曜は閉と解釈されます。
つまりこの値は「金曜は休み」という主張になります。
フラグは営業日と言っているので、その主張は誤りです。

判断内容は全件が `<業態>_conflicts.csv` の「採用した判断」列に残ります。

### 例外ルールの合成

定期週は部分パターンのみ採用します。

```
採用する    土=第1,3,5週が休み  →  Sa[1,3,5] off
採用しない  日=第1週から第5週すべて休み  →  毎週フラグの 日=0 と同義なので出力しない
```

第1週から第5週すべて休みの指定は「毎週その曜日は休み」と同義で、
時刻の有無に既に反映されているためです。

その他の休診日は自由記述から日付を抽出します。
区切り文字、桁揃え、スラッシュ表記、範囲表現の揺れに対応し、94.3%から日付が取れます。

```
01月01日，01月02日，01月03日，12月30日，12月31日  →  Dec 30-Jan 03
年末年始（12月29日～1月3日）                      →  Dec 29-Jan 03
12/29~1/3                                     →  Dec 29-Jan 03
```

年をまたぐ連続は1本の範囲にまとめます。

1本の範囲が31日を超える場合は、終点の誤入力とみなして採用せず、原文を備考に残します。

```
8/14-5/16（改行）12/29-1/3
  →  Dec 29-Jan 03 だけを採用
  →  備考に [31日超の範囲:8/14-5/16] を残す
```

判定は合計日数ではなく1本の範囲の長さに対して行います。
個別日付の羅列は何日あっても正当だからです。
実際に60日分の個別日付を並べている施設があり、それは正しい入力です。

日付を特定できない期間（`GW`、`お盆`、`年末年始`、`創立記念日`、`夏季`）は、
fallback ルールのコメントとして残します。

`||` の後ろに置くことが必須です。
通常ルールとして書くと全時間帯を上書きし、平日まで休診判定になります。
参照実装で 2026年1月14日（水）の状態を確かめた結果は次のとおりです。

```
Mo,Tu,We,Th,Fr 09:00-17:00; "GWは休診"           水曜が閉になる
Mo,Tu,We,Th,Fr 09:00-17:00; "GW" off             水曜が閉になる
Mo,Tu,We,Th,Fr 09:00-17:00; PH off || off "GWは休診"   水曜は開のまま
```

### 救急科の分離

救急科（コード `09010`）は24時間と深夜の運用が正常です。
外来の `opening_hours` からは分離し、誤りではなく性質の異なるデータとして
`<業態>_emergency.csv` へ退避します。

```
天使病院  救急科  月 帯1  00:00-12:00
天使病院  救急科  火 帯1  00:00-12:00
```

この `00:00-12:00` を外来と混ぜると、施設全体の開始時刻が `00:00` に引きずられます。
当初これを外れ値として扱っており、外れ値の最大の供給源（15%）になっていました。

## healthcare:speciality

### 対応表

126コードすべてに対応付けています（exact 73、broader 53、未対応 0）。
名称は523種と揺れるので、対応付けはコードを鍵にします。

`mapping/speciality_mapping.csv` の実際の行を示します。

```
業態      コード  診療科目名        OSM値                          確度      備考
(既定)    09003  リハビリテーション科  physiatry                     exact    wikiの定義が該当
(既定)    01027  漢方内科         traditional_chinese_medicine  broader  漢方は中医学と同一ではない
(既定)    02022  乳腺外科         surgery                       broader  対応値が無い。973施設と多く要検討
dental   08991  インプラント       dentistry                     broader  歯科では口腔外科ではない
```

「対応の確度」列は3値です。
`exact` は OSM 側に対応する値があるもの、`broader` は対応する値が無く上位概念に丸めたもの、
`none` は対応付けできず出力しないものです。
`broader` の行には、なぜ丸めたかを備考に書いています。

127コードすべての対応と、どの診療科がどの値に集まるかの逆引きは
[speciality-mapping.md](speciality-mapping.md) にあります。

最後の行のように、同じコードが業態で別の意味を持つ場合は業態別の上書きを持てます。
「業態」列が空の行が既定で、業態名の入った行がその業態でのみ優先されます。

値は OSM wiki の文書化値を優先します。
文書に無いが実運用で定着している値は、出典を明記して使い分けます
（`dentistry` は taginfo 1,518件、`dialysis` は483件）。

### 255文字の上限

OSM のタグ値は255文字が上限です。
診療科をすべて列挙すると大学病院クラスで500文字を超えるため、
上限を超えた施設だけ段階的に短縮します。

```
段階1 短縮なし（6,612施設）
  慈啓会病院  internal;gastroenterology;traditional_chinese_medicine;geriatrics;
             psychiatry;physiatry;diagnostic_radiology        108文字

段階2 畳む（706施設）
  札幌医科大学附属病院  27値では255文字を超えるため細分値を上位科へ畳んで22値
                    internal;neurology;pulmonology;cardiology;...  248文字

段階3 general 単独（397施設）
  市立札幌病院  畳んでも収まらないため general の1語のみ            7文字
              畳む前の31値は備考に保存
```

段階3は wiki の `general` が「General practitioner or general hospital」と
定義されていることに依ります。
31診療科を持つ病院は総合病院にあたり、語彙の趣旨に合致します。

数字は病院の例です。
診療所は畳み30件と `general` 1件、歯科診療所は畳み1件のみでした。

## 名称

### 運営主体の除去

「最後のトークンを施設名とする」規則は採用しません。
病院では97.9%成立しますが、助産所では25.9%まで落ちるためです（[data.md](data.md) 参照）。

代わりに、運営主体と識別できるトークンだけを先頭から取り除き、識別できなければ何も削りません。
判定は3つの対応表に分かれます。

| ファイル | 役割 | 例 |
|---|---|---|
| `name_entity_prefixes.csv` | 法人格39種。長い順に照合する | `医療法人社団`、`社会福祉法人` |
| `name_entity_suffixes.csv` | 法人名の接尾辞 | `会`、`組合`、`厚生連` |
| `name_facility_words.csv` | 施設種別語 | `病院`、`薬局`、`相談室` |

長い順の照合は必須です。

```
特定医療法人社団慶愛会札幌花園病院
  短い順に当てた場合  特定医療法人 で止まり → 社団慶愛会札幌花園病院（社団が残る）
  長い順に当てた場合  特定医療法人社団 が当たり → 慶愛会札幌花園病院
```

3つ目の規則が効きます。
先頭が施設種別語で終わらず、末尾が終わる場合だけ運営主体とみなすので、危険な例が保護されます。

```
医療法人社団明日佳　札幌明日佳病院  → 札幌明日佳病院      明日佳は施設種別語で終わらない
三戸町国民健康保険　三戸中央病院    → 三戸中央病院        保険は施設種別語で終わらない
ふじい薬局　明野調剤              → ふじい薬局 明野調剤   先頭が薬局で終わるので削らない
オアシス　ファーマシー            → オアシス ファーマシー  末尾が施設種別語でないので削らない
```

トークンを落とした結果、先頭に再び法人格が現れることがあります。

```
医療法人社団温光会　医療法人内藤病院
  1回目  温光会 が接尾辞に当たり除去 → 医療法人内藤病院
  2回目  医療法人 が法人格に当たり除去 → 内藤病院
```

そのため除去処理は収束するまで繰り返します。

| タグ | 内容 | 件数 |
|---|---|---:|
| `name` | 運営主体を除いた施設名 | 206,043 |
| `official_name` | 元の正式名称（法人格を含む完全名） | 206,043 |
| `short_name` | 略称 | 業態による |
| `name:ja-Hira` | フリガナをひらがな変換 | 158,358 |

| `name:en` | 英語と判別できたもの | 83,552 |

`name:ja-Hira` は taginfo で395,616件使われており、`name:ja_kana`（43件）ではなく
こちらが慣行です。

### 読みとの対応

フリガナは法人格を含む読みです。

```
名称     株式会社アミヤ薬局
フリガナ  カブシキガイシャアミヤヤッキョク
name    アミヤ薬局
```

`name` から運営主体を除いた施設では読みが対応しなくなるため、
`name:ja-Hira` を出力せず理由を備考に残します。
上の例で `かぶしきがいしゃあみややっきょく` を出すと、`name` の読みとして偽になります。

### name:ja-Latn の検証

音写をそのまま入れると、この名前のローマ字表記であるという主張が偽になる場合があります。

```
名称=旭川脳神経外科循環器内科病院   音写=Asahikawa Noge        途中で切れている
名称=医療福祉センター札幌あゆみの園  音写=sapporoayuminosono    先頭が欠落
```

そこでフリガナから独立にヘボン式ローマ字を導出して突き合わせ、一致したものだけ採用します。

```
採用する例
  name=長生会病院      読み=ちょうせいかいびょういん     音写=Chouseikai Byouin
  name=自衛隊札幌病院   読み=じえいたいさっぽろびょういん   音写=Jieitai Sapporo Byoin

採用しない例
  name=札幌厚生病院    音写=Sapporo Kousei Byoin   読みは運営主体を含み対応しない
```

| 判定 | 件数 | 比率 |
|---|---:|---:|
| 完全一致 | 71,340 | 82.9% |
| ほぼ一致（類似度0.9以上） | 7,782 | 9.0% |
| 略記など（0.75以上） | 3,455 | 4.0% |
| 不一致 | 3,451 | 4.0% |

比較時は長音（`ou`、`oo`、`uu`）、訓令式との揺れ（`sy` と `sh`、`ti` と `chi`）、
連続文字を畳んで吸収します。
表記の流儀の違いで落とさないためです。

出力には元の音写を使います。
導出したローマ字は `Sapporoikadaigakufuzokubyouin` のように語の区切りが無い続き綴りになるのに対し、
元データは `Sapporo Medical University Hospital` のように語間に空白があり読みやすいためです。

## 住所

### 解析を外部に任せる

住所を `addr:*` に分解する処理は `nja-osm-tags` に任せ、子プロセスで呼びます。
日本の住所の階層は都道府県、郡、市区町村、政令市の区、町字、丁目、街区、住居番号と分かれ、
表記の揺れも多いため、この対応付けだけで独立した判断の集まりになります。
`nja-osm-tags` は ESM の TypeScript で書かれており、CommonJS のスクリプトからは
`require` できないので、標準出力を受け取る形にしています。

`nja-osm-tags` には座標の列を渡しません。
渡すと向こう側で元データの座標と代表点の合流が先に済み、どちらを採ったのかが
出力から読み取れなくなります。
渡さなければ返ってくる座標は常に住所から得たものだけになるので、合流の規則を
`addr_columns.js` の1箇所に置けます。

### 公開 API は使わない

住所データの取得先は環境変数 `NJA_API_BASE` で指定します。
`build_addr.js` は起動時にこれを確かめ、未設定か公開 API を指していれば終了コード2で落ちます。

`nja-osm-tags` は取得先が未設定なら Geolonia の公開 API を読みます。
20万件を通すと1件ごとに問い合わせが出るうえ、公開 API が配信しているデータは
手元に構築したものより古くなります。
どちらも黙って起きてほしくないので、走り出す前に止めます。

値が実在するかどうかは `nja-osm-tags` の `applyApiBase` が起動時に確かめるので、
こちらでは二重に検査しません。

### どちらの座標を採るか

元データの緯度と経度が両方とも有効なら、原則としてそれを使います。
片方でも欠けていれば住所から得た座標に回します。
片方だけを採ると、欠けたほうが `0` のまま残って赤道上の座標になるためです。
例外は次の節に書く、元データの座標がジオコーダ座標から大きく離れている場合です。

住所から得た座標は、位置レベルが8のときだけ採用します。
8は住居表示の位置を意味します。
3は町字と丁目の代表点で、建物から数百メートルずれるため採用しません。

| 座標の出典 | 件数 |
|---|---:|
| 原データ | 189,514 |
| ジオコーディング | 6,986 |
| なし（地番方式） | 5,143 |
| なし（位置レベル不足） | 4,400 |
| 合計 | 206,043 |

### 元データの座標がジオコーダ座標から離れている場合

元データの座標が、住所から求めたジオコーダ座標より1km以上離れている行は、
ジオコーダ座標を採ります。
元データの座標が誤っていることがあるためです。
同じ座標を別の市区町村の施設が共有している例が実在します。

置き換えるのは次の3つを満たす行だけです。

| 条件 | 理由 |
|---|---|
| 位置レベルが8 | 3の代表点と比べると、正しい座標まで数百メートル離れて見える |
| `番地の根拠` が `照合済み` | `推定` の番地は入力文字列を機械的に切ったもので、別の場所を指しうる |
| 距離が1kmを超える | 敷地の広い病院でも1kmは超えない |

閾値は実測から決めました。
診療所32,626件で比較したところ、距離は中央値15m、99パーセンタイル413mでした。
1kmを超えるのは119件（0.36%）で、その全てが `照合済み` です。
`推定` の番地が原因で遠くを指す組み合わせは1件もなかったので、条件を絞っても取りこぼしません。

| 業態 | 置き換えた件数 |
|---|---:|
| 病院 | 10 |
| 診療所 | 119 |
| 歯科診療所 | 74 |
| 助産所 | 16 |
| 薬局 | 67 |
| 合計 | 286 |

置き換えた286件の距離は中央値2,944m、最大979,895mです。
100kmを超えるものが17件あり、元データの座標の誤りと判断できます。

置き換えた行は `座標の出典` が `ジオコーディング` になり、`要確認` が立ちます。
`備考` に距離を書き、元の値は `元_緯度` と `元_経度` に残すので、後から戻せます。
座標を補完した行と区別するには、`元_緯度` に値があるかどうかを見ます。

### 距離では判定できない誤り

1kmの規則は位置レベル8の行にしか使えません。
比較の相手が無い行や、代表点しか得られない行の誤りは見つけられません。

```
  位置レベル3   医療法人ＭＫクリニック          宮崎県都城市早鈴町１５１２
  位置レベル2   よしむら循環器内科クリニック      宮崎県小林市細野１６０６－１
  位置レベルなし  おりたこどもクリニック          宮崎県児湯郡高鍋町大字上江８２７９
  位置レベル8   みやざき駅前眼科             宮崎県宮崎市広島２－１１－１１
```

同じ座標を共有する9件ですが、位置レベル8は2件だけです。
残る7件は距離で判定できません。

### 元データの穴埋めの座標

上の9件は元データの誤記ではありませんでした。
元データは座標を持たない施設に、都道府県庁の代表点を入れています。
`31.911095,131.423893` は宮崎県庁の位置で、宮崎県の18施設がこの1点に乗っています。

全業態の元データ座標を突き合わせると、2つ以上の市区町村が完全に同じ座標を
共有する地点が21あり、152行がそこに乗っていました。

| 種類 | 地点 | 行 |
|---|---:|---:|
| 都道府県庁の代表点 | 13 | 111 |
| 丸めた値（`38.0,140.0` など） | 2 | 27 |
| 実在の建物 | 6 | 14 |

都道府県庁の代表点であることは、住所データで都道府県名だけを解決して確かめました。
`nja-osm-tags` は都道府県名だけの入力に位置レベル1（`都道府県庁所在地`）の点を返します。
13地点のうち11点はその点から100m以内、残る2点も225mと107mで県庁の街区の中でした。

### 県庁からの距離では判定できない

県庁の代表点に近いことを条件にはできません。
県庁の中や隣にも医療機関があるためです。

```
      4m  高知県高知市丸ノ内１丁目２－２０  (地方職員共済組合　高知診療所)
      7m  福岡県福岡市博多区東公園７番７号　県庁行政棟北館地下１階  (県庁内クリニック)
     10m  大分県大分市大手町３－１－１  (県庁歯科診療所)
     69m  岡山県岡山市北区内山下２丁目４ー６岡山県庁西庁舎２階  (岡山済生会県庁内診療所)
```

自県の県庁代表点から300m以内にある515行のうち、404行は実在の施設でした。

### 穴埋めを見分ける2つの条件

効いたのは距離ではなく、同じ座標を別の市区町村が共有していることです。

| 条件 | 根拠 |
|---|---|
| 同じ座標を2つ以上の市区町村の施設が共有する | 1つの点が両方の住所であることはありえない |
| 緯度と経度がともに0.1度の格子に乗る | 0.1度は約11kmで、施設の位置の精度ではない |

県庁代表点から300m以内の515行を、自分の住所から得た点と突き合わせた結果です。

```
                  300m以内    300m超1km以内    1km超      座標なし
市区町村2以上                0            10      72        29   計111
単一市区町村              350            15      15        24   計404
```

市区町村をまたいで共有された111行は、1件も自分の住所の近くにありませんでした。
単一の市区町村で共有する404行は350件が300m以内で、同じ建物に入る施設の重なりです。
この分離を使い、共有している行でも自分の住所から得た点が300m以内にあれば残します。
恵比寿銀座クロスビルの3階と4階に入る2院は、住所から得た点が12mなのでこの例外で残ります。

0.1度の格子の条件は、県庁とは無関係な丸め値のためにあります。
格子に乗る36行のうち、距離を測れたものは1,898mから113,085m離れていました。
`宮崎県都城市高崎町` の施設に `38,135`（島根沖の海上）が入っている例もあります。

### 穴埋めと判定した座標をどうするか

`座標の出典` を伏せ、住所から得た点で付け直します。
付け直す先は `住所_lat` `住所_lon` `住所_位置レベル` で、`build_addr.js` が
元データの座標を採った行にも必ず残します。
位置レベルが8に満たなければ座標を持たない行になります。
いずれの場合も `要確認` が立ち、`備考` に理由が入ります。

判定は業態をまたがないと成立しません。
同じ県庁の代表点に病院と薬局が1件ずつ乗っている場合、業態ごとに見ると
市区町村が1つに見えてしまいます。
そのため `build_addr.js` の中ではなく、全業態が揃ってから
`fix_placeholder_coords.js` を走らせます。
`npm run build` は `prep:*` を5業態ぶん回し、`fix:coords` を挟んでから
`osm:*` を回します。

`coord_cross_city` の一覧は残します。
新しい条件で拾えない重なりが出たときに気づくためです。

### 地番の座標は使わない

日本の住所は2つの体系で解決されます。
住居表示はアドレス・ベース・レジストリ由来で、こちらは出力できます。
地番方式はライセンス上 OSM に投入できないため、`nja-osm-tags` は地番に由来する
番地も座標も返しません。

そのため地番方式と判定された5,143件は、座標を補完せずに `補完しなかった理由` 列へ
`地番方式` と記録します。
件数を数えられる形で残すので、あとから方針を変えたときに対象を特定できます。

### 番地の根拠

`addr:block_number` と `addr:housenumber` をどこから得たかを `番地の根拠` 列に記録します。
値は `照合済み` `推定` `なし` の3種で、判定は上から順に当たった枝で決まります。

| 値 | 条件 | 番地の出どころ |
|---|---|---|
| `なし` | 地番方式の住所 | 出力しない |
| `照合済み` | 住居表示の明細レコードが取れた | 台帳のレコード |
| `なし` | 町字を特定できない、国土数値情報由来で明細を持たない、住居表示未実施のいずれか | 出力しない |
| `推定` | 町字は住居表示実施済みだが明細と一致しない | 入力文字列 |

`照合済み` は台帳の明細レコードから `blk_num` と `rsdt_num` を取ります。
入力文字列の数字は使わないので、その街区符号と住居番号の組み合わせは実在します。

`推定` は入力文字列の先頭にある数字列を機械的に切り、1つ目を街区符号、2つ目を住居番号に割り当てたものです。
町字が住居表示を実施済みなのは台帳で分かっていますが、その番地が実在するかは確認していません。
3つ目以降の要素は `fixme` に回します。

| 業態 | 照合済み | 推定 | なし |
|---|---:|---:|---:|
| 病院 | 2,461 | 921 | 4,333 |
| 診療所 | 34,580 | 11,983 | 33,592 |
| 歯科診療所 | 23,594 | 8,147 | 22,896 |
| 助産所 | 604 | 354 | 1,180 |
| 薬局 | 24,064 | 9,526 | 27,808 |
| 合計 | 85,303 | 30,931 | 89,809 |

### 推定に誤りが混ざる兆候

`推定` 30,931 件のうち、元の所在地が `番地` 表記のものが1,587件（5.1%）あります。
`番地` は地番の書き方で、住居表示なら `番` と `号` を使います。
住居表示を実施済みの町字に地番で書かれた住所が混ざると、その数字が街区符号として出ます。

```
北海道旭川市豊岡３条６丁目１７６番地１０７
  → addr:block_number=176, addr:housenumber=107
```

`addr:block_number` が100を超えるものが1,351件（4.4%）あります。
住居表示の街区符号としては不自然で、同じ現象の別の見え方だと考えられます。

残る81.0%は `３－１５` のようにハイフンだけの表記で、書き方からは判別できません。
上の2つの数字は下限であって、誤りの総数ではありません。

明細と一致しない理由は特定していません。
入力の誤記、台帳の更新遅れ、住居表示への切り替え途中の区域などが考えられますが、
区別する手がかりを現在の出力は持っていません。

### 番地の根拠で絞る

投入時に `推定` を採るかどうかは決めていません。
両方を出力し、`番地の根拠` 列で後から絞れる形にしてあります。

`照合済み` だけを採るなら、`<業態>_osm.csv` を `番地の根拠` で絞り込みます。
この列は `<業態>_geocoded.csv` にあり、`<業態>_osm.csv` には含まれないので、ID で突き合わせます。

```bash
python3 -c "
import csv, io
src = {r['ID']: r['番地の根拠'] for r in csv.DictReader(io.open('output/hospital_geocoded.csv', encoding='utf-8-sig'))}
rows = list(csv.DictReader(io.open('output/hospital_osm.csv', encoding='utf-8-sig')))
keep = [r for r in rows if src.get(r['ID']) != '推定']
print(len(rows), '->', len(keep))
"
```

`推定` を落としても施設は消えません。
`addr:block_number` と `addr:housenumber` だけを外し、町字までの階層と座標は残す選択もできます。
町字までは台帳由来で、番地の根拠とは別に確定しているためです。

### 未解釈の部分は捨てない

住所のうち `addr:*` に落とせなかった部分は `note` に残します。
66,005件が該当し、内訳は次のとおりです。

| 中身 | 件数 |
|---|---:|
| 建物名や階や部屋番号 | 36,975 |
| 数字だけ | 13,936 |
| その他 | 10,605 |
| 数字と建物情報の混在 | 4,489 |

数字で始まるものが18,425件あり、住居表示を実施していない町字で地番が残った形が多くを占めます。
値の出自は元データの住所文字列であって地番データベースの参照結果ではないため、
そのまま残しています。
投入前に人手で確認する対象として、検証器が `addr_note_chiban` で件数を出します。

番地の要素が3つ以上あった3,364件には `fixme` が付きます。
2要素までは推測を含まないため付けません。

## 結合

### 何を結合するか

タグごとに生成した結果を、施設の ID で1つの行にまとめます。

| 結合元 | 取り出すもの |
|---|---|
| `<業態>_geocoded.csv` | 座標と住所、座標の出典、`addr:*` の9列 |
| `<業態>_names.csv` | `name` 系のタグ |
| `<業態>_opening_hours.csv` | `opening_hours` |
| `<業態>_speciality.csv` | `healthcare:speciality`（3業態のみ） |
| 施設票 | `website` の元になる URL、病床数 |

出力は CSV と GeoJSON の2つです。
CSV は表計算ソフトで一覧を確認するため、GeoJSON は JOSM で開いて既存の OSM データに
重ねるためです。
同じ内容なので、どちらか一方だけを見れば済みます。

GeoJSON の座標は `[経度, 緯度]` の順で書きます。
順序を取り違えると、日本の施設は経度が緯度として解釈されて全てオーストラリア西方の
海上に飛びます。
検証器はこの取り違えを値域で検出します。
日本の経度域（122度から154度）と緯度域（20度から46度）は重ならないため、
入れ替わった座標は必ずどちらかの範囲を外れます。

### 座標が無い施設は出力しない

9,642件は座標が得られず、OSM のノードを作れないため出力しません。

| 業態 | 出力 | 座標が無く除外 |
|---|---:|---:|
| 病院 | 7,526 | 189 |
| 診療所 | 77,117 | 3,038 |
| 歯科診療所 | 52,617 | 2,020 |
| 助産所 | 1,786 | 352 |
| 薬局 | 57,355 | 4,043 |
| 合計 | 196,401 | 9,642 |

内訳は地番方式が5,187件、位置レベル不足が4,455件です。

除外した施設は `<業態>_geocoded.csv` に残るので、どれが落ちたかを追えます。
座標が住所から付与したものかどうかは `座標の出典` 列に入ります。

### 施設種別のタグ

業態から `amenity` と `healthcare` を決めます。
対応は `mapping/facility_tags.csv` に外出ししています。

```
業態        条件           amenity   healthcare
hospital                  hospital  hospital
clinic      病床1以上       clinic    clinic
clinic      病床0または空欄  doctors   doctor
dental                    dentist   dentist
maternity                 (なし)     midwife
pharmacy                  pharmacy  pharmacy
```

助産所に `amenity` を付けないのは、`healthcare=midwife` に対応する `amenity` の値が
OSM に存在しないためです。

診療所だけ条件が2つあります。
医療法の診療所は19床以下で、無床の個人開業医から有床の施設までを含みます。
OSM の `amenity=doctors` は個人開業医の診療室、`amenity=clinic` はそれより規模の大きい
施設を指すため、1つの値には対応しません。
そこで病床数で分けています。

この分類は暫定です。
病床数が空欄の31,399件を無床とみなして `doctors` に寄せていますが、
空欄は未記入であって無床の証拠ではありません。
診療所78,083件のうち73,809件がこの推定に該当し、全件に要確認が立ちます。
一律 `clinic` にする案もあり、どちらを採るかはコミュニティでの合意で決まります。

### website の補正

元データの URL には形式の誤りが混じるため、直してから出力します。

```
goryokai.com          → https://goryokai.com     スキームが無いので https を補う
http//www.ssn-hp.jp   → http://www.ssn-hp.jp     コロンの脱字を補う
```

コロンの脱字は書かれているスキームをそのまま活かします。
裸のドメインはスキームが分からないので `https` を補います。
現在のウェブでは `https` が既定で、`http` のみのサイトも `https` へ転送されるのが
通例のためです。
どちらも元データに無い文字を足しているので、補った事実を備考に残します。
全業態で9,260件を補いました。

次の3つは出力しません。

```
https://www.bing.com/ck/a?...        検索エンジンの転送 URL。施設のサイトではない
（300文字の URL）                     OSM のタグ値の上限を超える
http:/www.aizenkai.or.jp/            スラッシュが1本。どう直すか決められない
```

落とした974件も、元の値を備考に残します。

### opening_hours の短縮

タグ値が255文字を超える29件は、末尾の規則から落として収めます。

```
東京中央卸売市場診療所
  短縮前 284文字  Mo,Tu,We,Th,Fr 08:40-12:00,13:20-15:00; Sa 08:40-12:00; PH off;
                  Jun 04,Jun 11,Jun 18,... （個別の休診日が60件以上続く）
  短縮後  62文字  Mo,Tu,We,Th,Fr 08:40-12:00,13:20-15:00; Sa 08:40-12:00; PH off
```

規則は「基本時間 → 定期週 → 祝日 → 特定日の休み」の順に並ぶので、末尾は必ず日付指定です。
曜日ごとの時刻が最も価値が高く、個別の休診日を失っても営業時間の主要部は残ります。
29件すべてで落ちたのは日付指定1件だけで、曜日ごとの時刻と `PH off` は全件残りました。

落とした内容は備考に原文のまま記録します。
短縮前の値は `<業態>_opening_hours.csv` にあるので、そちらから復元できます。

### ref 系のタグは付けない

医療情報ネットの ID を OSM のどのキーで持つかは、コミュニティでの合意が要ります。
勝手にキーを決めると、後から付け直す作業が発生します。
`ID` 列は全ての出力に残すので、合意後に付け直せます。

### source タグ

PDL1.0 は加工した情報について、加工した旨と加工者の明示を求めています。
全ての地物に次の値を入れます。

```
source=厚生労働省 医療情報ネットのオープンデータ (2026-06-01)
```

## 検証

### 独立した実装で確かめる

生成側（Python）と検証側を独立させ、自前の正規表現では気づけない誤りを拾います。
`opening_hours` は OSM の事実上の標準実装 `opening_hours.js` で全件を検証します。

この検証で実際に見つかった欠陥は2つあります。

```
08:30-08:30 という出力  ゼロ長とも24時間とも読める曖昧な値だった
コメントの置き場所      通常ルールとして書いており平日まで休診判定になっていた
```

### 検証器そのものを逆テストする

何も検出しない検証器は無意味です。
既知の不正な値をかけて、狙った分類で検出されることを確かめます。
`tests/known_bad.csv` に7件のフィクスチャを固定しています。

```
正常な値                    検出されないのが正しい
コメントを通常ルールに誤配置    never_open として検出されるべき
ゼロ長区間                  zero_span として検出されるべき
構文エラー                  error として検出されるべき
第1土曜のみ開院              検出されないのが正しい（偽陽性の確認）
正しいコメント配置            検出されないのが正しい
日跨ぎの当直帯               warning が出るのが既知の挙動
```

この逆テストで検証器自身の穴が見つかりました。
コメントだけのルールは期間全体を `unknown=true` の1区間で埋めるため、
区間数を数えるだけの実装では破損を見逃していました。
確実に開いている区間だけを数えるよう直しています。

### 偽陽性を避ける

「一定期間で一度も開かない」の判定は窓の取り方が難しく、2度修正しています。

```
窓が1週間   Sa 09:00-12:00; Sa[2,3,4,5] off
            第1土曜のみ開院する施設。窓に第1土曜が入らず偽陽性

窓が5週間   Mo 13:30-14:30; Mo[1,3,4,5] off; PH off
            第2月曜のみ開院する施設。窓に入る唯一の第2月曜が
            成人の日（1月の第2月曜）と重なり PH off で閉まるため偽陽性
```

現在は5週間で高速に判定し、そこで引っかかった数件だけ13週間で再確認する2段階です。
全件を長い窓で走査すると、数万件では時間がかかりすぎます。

### 現在の結果

全5業態206,043施設で、パースエラー、語彙エラー、タグ値長超過、値の重複はいずれもゼロです。
残る警告は日跨ぎが翌日ルールと衝突するもので、データが実際にそうなっている以上は欠陥ではありません。
既知の挙動として逆テストに固定しています。
